## 1. 제품 개요

### 1.1 문제 정의
| 문제 | 현재 상황 |
|---|---|
| 해외 축구 소식은 영어 중심 | BBC·Sky·Athletic 등 1차 소스는 영어. 국내 포털은 한국 선수 위주이고 2차 인용이 많음 |
| 소식이 흩어져 있음 | 뉴스는 포털, 순위는 앱, 이적은 X(트위터), 한국 선수는 검색 — 매일 여러 곳을 돌아야 함 |
| 시간대 불일치 | 유럽 경기는 KST 새벽에 끝남. 아침에 "밤사이 무슨 일이 있었나"를 빠르게 파악할 수단이 부족 |
| 이적 루머의 신뢰도 판단이 어려움 | 출처별 신뢰도 차이가 크지만 일반 팬은 구분하기 어려움 |

### 1.2 제품 비전
**"출근길 3분이면 밤사이 유럽 축구를 다 따라잡는다."**
매일 아침(유럽 서머타임 기간 07:00 · 유럽 표준시 기간 07:30 KST), 밤사이 경기 데이터를 한국어 브리핑으로 정리하고, 해외 1차 소스의 소식은 원제목 그대로 같은 사건끼리 묶어 한국어로 분류한 뒤 원문으로 연결하는, 빠르고 세련된 공개 웹서비스. (D23·D24·D26)

### 1.3 가치 제안
1. **핵심만** — 밤사이 경기는 한국어 "오늘의 5줄" 브리핑으로, 뉴스는 같은 사건을 하나로 묶고 한국어 태그(대회·팀·선수·이적 단계)로 정리 (D23·D24)
2. **원문 존중** — 해외 기사는 번역·요약하지 않고 원제목 그대로, 매체명·원문 링크 필수 (D23)
3. **한곳에서** — 뉴스·순위·일정·한국 선수·이적·A매치
4. **신뢰도 표시** — 이적 소식에 출처 Tier 배지
5. **아름답게** — 광고 없는, 세련되고 모던한 읽기 경험

### 1.4 제품 원칙 (의사결정 기준)
충돌 시 위쪽이 우선한다.
1. **법·약관 준수** — 저작권·RSS 약관·robots.txt를 어기는 기능은 만들지 않는다.
2. **정확성** — 입력에 없는 사실은 쓰지 않는다. 모르면 비워 둔다.
3. **비용 상한** — 월 $3를 넘는 기능은 설계를 바꾸거나 보류한다.
4. **디자인 품질** — 세련되고 모던한 디자인이 제품의 핵심 차별점이다. 기능을 줄여도 품질은 지킨다.
5. **운영 무인화** — 사람 손이 매일 필요한 기능은 만들지 않는다.

### 3.2 핵심 사용 시나리오
1. **아침 브리핑** — P1이 발행 직후 출근길(유럽 서머타임 기간 07:10 · 표준시 기간 07:40 무렵, D26)에 홈 접속 → 상단 "오늘의 5줄"(경기 데이터 한국어 브리핑)로 밤사이 결과 파악 → 뉴스 피드에서 한국어 태그로 관심 카드를 골라 → 원문 링크로 이동. (D23·D24)
2. **내 선수 확인** — P2가 마이 팀에 등록한 선수의 어젯밤 출전·골 여부를 홈 상단에서 바로 확인 → 다음 경기 시간 확인 → 캘린더 구독.
3. **이적 추적** — P3가 이적 트래커에서 관심 선수의 상태(루머→협상→합의→확정)와 출처 Tier 확인.
4. **오늘 밤 계획** — P4가 퇴근길에 "오늘 밤 볼 경기"에서 빅매치·한국 선수 경기를 KST로 확인.
5. **스포일러 회피** 🆕 — 녹화 중계를 볼 예정인 사용자가 "결과 가리기"를 켜고 뉴스만 읽음.

### 4.1 내비게이션
- **모바일**: 하단 탭 바 5개 — 홈 · 뉴스 · 리그 · 한국 선수 · 마이
  (이적·A매치·오늘 밤은 홈 섹션과 상단 메뉴에서 진입)
- **데스크톱**: 상단 헤더 내비 + 3단 레이아웃(좌: 대회/필터, 중: 피드, 우: 오늘 밤 경기·한국 선수·순위 미니 위젯)
- 전역: 검색, 다크/라이트 토글, 결과 가리기 토글 🆕, "마지막 업데이트 HH:MM KST" 표시 🆕

### 4.2 홈 화면 구성 (위 → 아래)
1. **오늘의 5줄** 🆕 — 전날(KST) 경기 결과·순위 변동·득점자·한국 선수 출전 등 정형 데이터를 LLM이 한국어 뉴스체로 쓴 최대 5줄 브리핑, "AI 작성" 라벨 (3분 브리핑의 핵심, FR-22~29·FR-35, D24)
2. **내 팀 소식** — 팔로우 항목이 있을 때만 노출
3. **A매치 섹션** — A매치 기간에만 자동 노출
4. **한국 선수 하이라이트** — 어젯밤 출전·골·도움 요약 칩
5. **오늘 밤 볼 경기** — 최대 5경기, KST
6. **주요 뉴스 피드** — 중요도·시각 순, 카테고리 칩 필터
7. **이적 핫 리스트** — 상태 변화가 있었던 상위 5건
8. **리그 순위 미니** — 탭 전환(5대 리그 + UCL), 상위 5위

> **최상단은 '오늘의 5줄'로 확정**(§15 D2). 2번 이하 섹션 순서와 표현 방식은 디자인 시안 단계에서 2~3안으로 비교한 뒤 확정한다(§6.1).

## 5. 기능 요구사항

### 5.1 F1 · 뉴스 수집 파이프라인 (P0)
| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-01 | `configs/sources.json`에 등록된 소스만 수집. 필드: `id, name, type(rss/crawl/search/journalist/aggregator/analysis), url, lang, enabled, weight, tier, competitions, terms_checked, robots_checked` | `enabled:false` 또는 `terms_checked:false` 소스는 수집하지 않음. 목록·OG 크롤링을 하는 소스는 `robots_checked:false`여도 수집하지 않음 |
| FR-02 | 수집 우선순위: 공식 RSS → 기자·블로그(Substack RSS·목록 크롤링) → 뉴스 검색(GDELT — Google News RSS는 약관·robots상 사용 불가, §15 D25. GDELT는 약관상 가능하나 M0-27 실측에서 레이트 리밋·허용 목록 통과 0건으로 현재 비활성, M1 관찰 기간 재측정) → OG 메타 경량 크롤링. 검색 결과는 `configs/publisher-domains.json`에서 `allow`인 매체 도메인만 게시(목록에 없으면 차단). **본문 크롤링 금지** | 수집 결과에 본문 필드가 존재하지 않음 |
| FR-03 | 모든 수집 결과를 공통 형식으로 정규화: `title, url, publishedAt(UTC), summary(≤500자), source, author?, lang` | 스키마 검증(zod) 통과 |
| FR-04 | URL 정규화(utm·트래킹 파라미터 제거, AMP→원본) 후 해시로 중복 제거. `data/cache/seen-urls.json`(90일 보관)으로 과거 처리분 제외 | 같은 URL이 두 번 카드화되지 않음 |
| FR-05 | 제목 유사도 기반 **동일 사건 클러스터링** — 여러 매체의 같은 소식은 1개 클러스터, 출처 링크 여러 개. 분류 뒤 같은 경기(같은 두 팀 + 같은 스코어 + 12시간 이내 — 스코어 없는 기사는 대상 아님, D49 ②) 카드는 2단계로 합친다(D42) | **잘못 합친 카드 0건**(다른 사건이 한 카드로 사라지지 않음) + 같은 사건 중복 감소율을 주간 샘플 검수로 기록 (D42 — 2026-10-15 변경, 이전 '일일 중복 카드 0건') |

**DR-00 · 시안 우선 원칙 — 모든 디자인 구현은 반드시 아래 절차를 따른다.**

```
① 요구 정리 → ② 콘셉트가 서로 다른 시안 2~3개 제작 → ③ 사용자에게 제시·선택 요청
→ ④ 선택(또는 혼합 지시) 확정 → ⑤ DESIGN.md 반영 → ⑥ 구현
```

- 사용자의 선택 없이 디자인을 구현하지 않는다. "일단 기본 스타일로 만들고 나중에 바꾸기"도 금지.
- 시안은 **서로 다른 방향**이어야 한다(색만 바꾼 변형 금지). 각 시안에 콘셉트 이름, 한 줄 설명, 장단점을 붙인다.
- 시안 형식: 실제 데이터 샘플이 들어간 정적 HTML 목업 (`docs/design/<단계>/concept-a.html` …), 모바일 375px + 데스크톱 1280px 두 화면.
- 선택 결과·이유는 `docs/design/DECISIONS.md`에 기록.
- 디자인 게이트 위치:

| 게이트 | 시점 | 시안 범위 |
|---|---|---|
| **D0 전체 콘셉트** | M0 완료 후, M1 UI 착수 전 🆕 | 브랜드 무드, 컬러·타이포, 홈 + 뉴스 카드 |

### 8.2 주요 스키마 (초안, 최종은 plan.md에서 zod로 확정)

**뉴스 카드** — `data/news/YYYY-MM-DD.json`
```json
{
  "id": "c_8f3a1b2c4d",
  "t": "Liverpool open talks over new deal for defender",
  "s": [],
  "cat": "transfer",
  "comp": ["EPL"],
  "teams": ["liverpool"],
  "players": [],
  "imp": 4,
  "kr": false,
  "spoiler": false,
  "transfer": { "player": "…", "from": "…", "to": "…", "status": "negotiating", "tier": 2 },
  "src": [{ "n": "BBC Sport", "u": "https://…", "at": "2026-10-09T20:10:00Z", "tier": 2 }],
  "lang": "en",
  "ai": false,
  "created": "2026-10-09T21:30:00Z"
}
```
🆕 추가 필드: `spoiler`(결과 가리기 대상 — FR-21 코드 규칙 판정), `transfer.player/from/to`(트래커 집계용, 확인될 때만), `src[].tier`, `ai`(AI 작성 여부). 카드 ID는 `c_` + 16진수 10자리(§15 D15).
(D23) 위 예시는 해외 원제목 카드다 — `t`는 피드 제목 원문, `s`는 `[]`, `ai:false`. 해외·국내 뉴스 카드는 모두 `ai:false`이며 스키마는 바꾸지 않는다.

**일일 브리핑** (D24·D38) — `data/briefs/YYYY-MM-DD.json` → `{ date, generatedAt, runId, mode, lines: [{ text, ai, refs }] }`, `mode` = `llm`·`mixed`·`template`·`empty`, `refs` = 근거 경기·순위·선수 ID. 최종 zod는 plan 부록 A(M1-19).

**경기 기록 누적** (D27) — API-Football 경기 단건 조회에서 얻은 경기별 득점자·라인업(포메이션)·한국 선수 경기 기록을 M1부터 쌓아 시즌 누적(FR-61)·포메이션(FR-55)·주간 리포트(FR-91)에 쓴다. 저장 위치·스키마(집계 시작일 포함)는 M1 착수 시 초안을 제안하고 사용자 확인 후 plan 부록 A에 추가한다. 원본 응답은 커밋하지 않고 필요한 필드만 변환해 저장한다.

**이적 트래커** — `data/transfers.json`
```json
{ "id": "t_xxx", "player": "…", "from": "…", "to": "…", "status": "agreed",
  "bestTier": 1, "updated": "…", "history": [{ "at": "…", "status": "rumor", "card": "c_…" }] }
```

**실행 로그** — `data/runs.json`(prod) · `data/runs-dev.json`(dev, 개발자가 커밋 — §15 D18)
```json
{ "runId": "…", "env": "prod", "job": "collect", "startedAt": "…", "finishedAt": "…",
  "collected": 412, "clusters": 45, "summarized": 5, "downgraded": 0,
  "tokens": { "in": 0, "out": 0, "cacheRead": 0, "cacheWrite": 0 }, "costUsd": 0.0,
  "apiCalls": { "footballData": 18, "apiFootball": 26 },
  "sources": [{ "id": "bbc-football", "ok": true, "items": 40, "usable": 12 }], "status": "success" }
```
(D24) 필드 이름은 그대로 두고 `summarized`는 LLM이 작성한 브리핑 줄 수, `downgraded`(plan 부록 A)는 코드 템플릿으로 강등된 줄 수로 쓴다. 최종 형식은 plan 부록 A `RunLog`(2026-10-17 예시 갱신 — `clusters` = 선별 카드 수, 소스별 기록 `sources[]`, 토큰 `cacheRead`·`cacheWrite`, 발행되지 않은 실행은 `status: failed`로도 기록 — M1-27).
(D27) `apiCalls.apiFootball` 예시는 토요일 실측 기준(날짜 조회 2 + 경기 단건 24)이다. 하루 최대 약 35건, 계획 상한 60.

### 9.2 프롬프트·출력 규칙
- 프롬프트는 `configs/prompts/{summarize,team-profile,weekly-kr}.md`로 관리 — `summarize.md`는 일일 브리핑 프롬프트(파일명 유지, D24). 변경 시 샘플 10건(브리핑은 10일치 입력) 회귀 비교 🆕
- 입력은 데이터 API에서 받아 어댑터로 변환한 정형 데이터(JSON)만, 기사 텍스트 미포함 (D24)
- 출력은 짧은 키 JSON, `max_tokens` 상한, 브리핑은 최대 5줄·줄당 60자 내외 (D24)
- 일일 브리핑 설정 (D28): thinking은 **적응형 기본 + `effort:"medium"` 명시**, `max_tokens` ~~4,096~~ → **8,192**(D53). 근거는 M0-30 사실성이다(사람 검토). 기본 설정은 45/45줄이 입력과 일치했고, thinking을 끄면 15/20줄(틀린 순위 해석 2·근거 없는 서술 3)로 KPI 90%에 못 미쳤다. `effort:"low"`는 요청마다 thinking 여부가 달랐고 영어로 출력한 사례가 있었다. 실측 최대 출력은 2,040토큰(thinking 1,721 포함)이다. 잘리면 템플릿으로 강등되고 쓴 토큰은 버려지므로 약 2배로 둔다. 주간 호출의 값은 plan M3-07·M4-05에서 정한다
- 금지: 입력에 없는 사실·수치·인용, 추측성 평가, 선수에 대한 비하 표현
- 루머는 반드시 보도 형식("~가 보도했다")으로

### 9.3 비용 추정 (가정치 — 구현 시 실제 단가로 재계산)

### 9.4 품질 관리

- 주 1회 수동 검수: 브리핑 20줄(입력 데이터 대조·고유명사·문체) + 뉴스 카드 20건 코드 분류(카테고리·태그·이적 단계·spoiler) (D23·D24)
