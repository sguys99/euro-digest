## 1. 제품 개요

### 1.1 문제 정의
| 문제 | 현재 상황 |
|---|---|
| 해외 축구 소식은 영어 중심 | BBC·Sky·Athletic 등 1차 소스는 영어. 국내 포털은 한국 선수 위주이고 2차 인용이 많음 |
| 소식이 흩어져 있음 | 뉴스는 포털, 순위는 앱, 이적은 X(트위터), 한국 선수는 검색 — 매일 여러 곳을 돌아야 함 |
| 시간대 불일치 | 유럽 경기는 KST 새벽에 끝남. 아침에 "밤사이 무슨 일이 있었나"를 빠르게 파악할 수단이 부족 |
| 이적 루머의 신뢰도 판단이 어려움 | 출처별 신뢰도 차이가 크지만 일반 팬은 구분하기 어려움 |

### 1.2 제품 비전
**"출근길 3분이면 밤사이 유럽 축구를 다 따라잡는다."**
매일 07:00 KST, 해외 1차 소스를 한국어 3줄로 요약하고 원문으로 연결하는, 빠르고 세련된 공개 웹서비스.

### 1.3 가치 제안
1. **핵심만** — 기사당 제목 1줄 + 3줄 요약, 같은 사건은 하나로 묶음
2. **원문 존중** — 번역이 아닌 요약, 매체명·원문 링크 필수
3. **한곳에서** — 뉴스·순위·일정·한국 선수·이적·A매치
4. **신뢰도 표시** — 이적 소식에 출처 Tier 배지
5. **아름답게** — 광고 없는, 세련되고 모던한 읽기 경험

### 1.4 제품 원칙 (의사결정 기준)
충돌 시 위쪽이 우선한다.
1. **법·약관 준수** — 저작권·RSS 약관·robots.txt를 어기는 기능은 만들지 않는다.
2. **정확성** — 입력에 없는 사실은 쓰지 않는다. 모르면 비워 둔다.
3. **비용 상한** — 월 $3를 넘는 기능은 설계를 바꾸거나 보류한다.
4. **디자인 품질** — 세련되고 모던한 디자인이 제품의 핵심 차별점이다. 기능을 줄여도 품질은 지킨다.
5. **운영 무인화** — 사람 손이 매일 필요한 기능은 만들지 않는다.

## 5. 기능 요구사항

### 5.1 F1 · 뉴스 수집 파이프라인 (P0)
| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-01 | `configs/sources.json`에 등록된 소스만 수집. 필드: `id, name, type(rss/crawl/search/journalist/aggregator/analysis), url, lang, enabled, weight, tier, competitions, terms_checked, robots_checked` | `enabled:false` 또는 `terms_checked:false` 소스는 수집하지 않음. 목록·OG 크롤링을 하는 소스는 `robots_checked:false`여도 수집하지 않음 |
| FR-02 | 수집 우선순위: 공식 RSS → 기자·블로그(Substack RSS·목록 크롤링) → 뉴스 검색(Google News RSS·GDELT) → OG 메타 경량 크롤링. **본문 크롤링 금지** | 수집 결과에 본문 필드가 존재하지 않음 |
| FR-03 | 모든 수집 결과를 공통 형식으로 정규화: `title, url, publishedAt(UTC), summary(≤500자), source, author?, lang` | 스키마 검증(zod) 통과 |
| FR-04 | URL 정규화(utm·트래킹 파라미터 제거, AMP→원본) 후 해시로 중복 제거. `data/cache/seen-urls.json`(90일 보관)으로 과거 처리분 제외 | 같은 URL이 두 번 카드화되지 않음 |
| FR-05 | 제목 유사도 기반 **동일 사건 클러스터링** — 여러 매체의 같은 소식은 1개 클러스터, 출처 링크 여러 개 | 일일 중복 카드 0건 (샘플 검수) |
| FR-06 | 점수화: 소스 weight × Tier 가중치(Tier 1이 가장 높음, 값은 설정으로 조정) × 키워드(빅클럽·한국 선수·UCL·이적) × 클러스터 크기(보도 매체 수) × 최신성 → 상위 `MAX_ITEMS_PER_RUN`(기본 45) 선별 | 설정값 변경으로 선별 규모 조정 가능 |
| FR-07 | 수집 시간 창: 직전 성공 실행 이후 ~ 현재 (최대 36시간) 🆕 | 실행 실패 다음 날 소식 누락 없음 |
| FR-08 | 크롤러는 `scripts/crawlers/<site>.ts`로 분리. robots.txt 준수, User-Agent에 서비스명·연락처, 사이트당 2~3초 지연, 하루 1회 | 실패 시 해당 소스만 건너뛰고 GitHub 이슈 생성 |
| FR-09 | 크롤링 금지 대상: Transfermarkt, FBref, WhoScored, SofaScore, FotMob, 네이버·다음 포털, X(트위터), 유료 본문 | 코드 리뷰 체크리스트에 포함 |
| FR-10 | 분석 블로그(`type: analysis`)는 주 1회만 수집, LLM 요약 없이 제목+링크 | 팀 페이지 '더 읽을거리'에만 노출 |
| FR-11 | 소스 건강도 기록 🆕 — 소스별 최근 7일 성공률·수집 건수를 `runs.json`에 기록, 3일 연속 0건이면 이슈 생성 | 죽은 피드를 자동 감지 |

### 5.2 F2 · 요약·분류 (LLM) (P0)
| ID | 요구사항 | 수용 기준 |
|---|---|---|
| FR-20 | 신규 **영문·기타 외국어** 클러스터만 LLM 요약. 한국어 기사는 LLM 생략(RSS 요약 절단 또는 제목+링크). 한국어 카드의 분류(카테고리·태그·중요도·spoiler)는 코드 규칙(키워드·`names.ko.json`)으로 채운다 | 한국어 소스 LLM 비용 0 |

## 6. 디자인 요구사항

> **세련되고 모던한 디자인은 이 제품의 핵심 차별점이다.** 기능이 같아도 "읽고 싶은" 화면이어야 매일 돌아온다.

### 6.1 디자인 프로세스 규칙 (필수)

**DR-00 · 시안 우선 원칙 — 모든 디자인 구현은 반드시 아래 절차를 따른다.**

```
① 요구 정리 → ② 콘셉트가 서로 다른 시안 2~3개 제작 → ③ 사용자에게 제시·선택 요청
→ ④ 선택(또는 혼합 지시) 확정 → ⑤ DESIGN.md 반영 → ⑥ 구현
```

- 사용자의 선택 없이 디자인을 구현하지 않는다. "일단 기본 스타일로 만들고 나중에 바꾸기"도 금지.
- 시안은 **서로 다른 방향**이어야 한다(색만 바꾼 변형 금지). 각 시안에 콘셉트 이름, 한 줄 설명, 장단점을 붙인다.
- 시안 형식: 실제 데이터 샘플이 들어간 정적 HTML 목업 (`docs/design/<단계>/concept-a.html` …), 모바일 375px + 데스크톱 1280px 두 화면.
- 선택 결과·이유는 `docs/design/DECISIONS.md`에 기록.
- 디자인 게이트 위치:

| 게이트 | 시점 | 시안 범위 |
|---|---|---|
| **D0 전체 콘셉트** | M0 완료 후, M1 UI 착수 전 🆕 | 브랜드 무드, 컬러·타이포, 홈 + 뉴스 카드 |
| D1 대회·팀 화면 | M2 UI 착수 전 | 순위표, 팀 헤더, 폼 칩, 포메이션 다이어그램 |
| D2 한국 선수·이적 | M3·M4 UI 착수 전 | 선수 카드, 주간 리포트, 이적 상태 진행 바 |
| D3 아이콘·OG 이미지 | M5 전 | 앱 아이콘, 공유 카드, 빈 상태 일러스트 |

> basic_plan은 디자인을 M5에 두었으나, 시안 우선 원칙에 맞춰 **D0 게이트를 M1 앞으로 당긴다** (§15 D1 확정).

### 6.2 디자인 원칙
| # | 원칙 | 의미 |

## 9. LLM 요구사항

### 9.1 호출 지점 (이 외 LLM 호출 금지)
| 작업 | 주기 | 규모 | 방식 |
|---|---|---|---|
| 뉴스 요약·분류 | 매일 | ~45건 | Batches API, 10~20건 묶음, 프롬프트 캐싱 |
| 팀 한줄평 + 강점/약점 | 주 1회 | ~110팀 | Batches API, 20팀 묶음, 한 호출로 함께 출력 |
| 한국 선수 주간 총평 | 주 1회 | 1회 | Batches API |

### 9.2 프롬프트·출력 규칙
- 프롬프트는 `configs/prompts/{summarize,team-profile,weekly-kr}.md`로 관리, 변경 시 샘플 10건 회귀 비교 🆕
- 출력은 짧은 키 JSON, `max_tokens` 상한, 요약 3문장 고정
- 금지: 입력에 없는 사실·수치·인용, 추측성 평가, 선수에 대한 비하 표현
- 루머는 반드시 보도 형식("~가 보도했다")으로

### 9.3 비용 추정 (가정치 — 구현 시 실제 단가로 재계산)
| 작업 | 월 토큰(대략) |
|---|---|
| 뉴스 요약 | 45건 × 30일 × (입력 250 + 출력 150) ≈ 입력 34만 / 출력 20만 |
| 팀 한줄평 + 강점/약점 | 110팀 × 4주 × (입력 300 + 출력 180) ≈ 입력 13만 / 출력 8만 |
| 주간 리포트 | 4회 × (입력 2K + 출력 1K) ≈ 입력 1만 / 출력 0.4만 |
- 강점/약점 포함 후에도 Haiku 계열 + 배치 할인 + 캐싱 가정 시 **월 $1~2** → $3 상한 내. M1 첫 주 실측 후 PRD 비용 표 갱신.
- 뉴스 요약 출력 150토큰에는 이적 정보·spoiler 판정(FR-21, §15 D17)이 포함된다. 건당 +10~20토큰으로 추정하며 M0-30·M1-42 실측으로 확인한다.

### 9.4 품질 관리
- 주 1회 샘플 20건 수동 검수(체크리스트: 사실 일치, 고유명사, 카테고리, 이적 상태)
- 오류 신고 이슈는 라벨(`summary-error`)로 집계 → 프롬프트 개선 근거
