## 1. 요약

- **목표 미달 — 성능 점수 ≥ 95를 맞춘 페이지가 없다.** 측정한 10쪽 모두 devtools 방식 69~75점, simulate 방식 51~68점이다. 막는 지표는 **TBT(긴 작업)** 하나다.
- **LCP · CLS는 예산 안이다**(devtools 방식 — 실제로 늦춰서 잰 값): LCP 1.55~2.03초(가장 무거운 3쪽 팀 · 홈 · 뉴스가 2.0초 언저리, 기계 부하가 클 때 팀 2.45초), CLS 최대 0.0378(`/tonight/`), 나머지 ≤ 0.02.
- **TBT는 페이지 크기가 아니라 프레임워크 · 하이드레이션 바닥이 정한다.** DOM 372개인 `/tonight/`도 TBT 0.8~3.3초(4× CPU), DOM 10,457개인 EPL과 같은 점수대다. 마크업을 줄여도(이번 작업 −1~−9%) 점수가 움직이지 않았다(§5 교차 측정 — 측정 잡음 안).
- **이 기계의 측정 잡음이 크다.** 같은 쪽 TBT가 774~7,743ms까지 흔들렸다(Lighthouse `benchmarkIndex` 537~2,038 — 다른 작업 레인 · 다른 프로젝트 서버로 load average 6~22). 절대값보다 경향으로 읽는다. 조용한 CI 러너 값은 M5-08에서 처음 나온다.
- **마크업 경량화(2026-11-03 사용자 결정 — 화면 · FR-44 범위 불변)**: 반복 요소 9종의 긴 클래스 묶음을 `@utility`(globals.css §14) 짧은 이름으로 — 팀 111쪽 합 47.3 → **43.0MB(−9.1%)**, 바이에른 566 → 515KB(−9.1%), EPL 2.02 → 1.92MB(−5.0%). gzip 전송량은 −1~−3%(반복 글자는 원래 gzip이 잘 줄인다). 시각 불변(전후 픽셀 비교 76장 — §6).

### 2.1 스로틀링 방식 — devtools(기본) vs simulate

- **simulate**(Lantern — PageSpeed Insights와 같은 방식): 빠른 로컬 무제한 로드를 한 번 하고 그 그래프로 느린 망을 계산한다. 우리 사이트에서는 무제한 로드의 첫 페인트(약 1.2초 — 하이드레이션 긴 작업 뒤)보다 **웹폰트 4면(약 430KB, 우선순위 VeryHigh)이 먼저 끝나서** Lantern이 폰트를 FCP 필수 경로로 넣는다 → FCP 3.46~3.62초 · LCP 4.66~4.82초가 거의 모든 쪽에서 같은 값으로 나온다. 실제 느린 망에서는 `font-display: swap`이라 폴백 글꼴로 먼저 그린다(M1-39 실측 · 아래 devtools 값). 무제한 로드의 첫 페인트가 우연히 폰트보다 빨랐던 실행(UCL · 날짜 페이지 각 1회)은 FCP 1.32~1.57초로 떨어졌다 — 시뮬레이션 산출물이라는 증거.
- **devtools**: 실제로 망 · CPU를 늦춰서 잰다(M1-39 측정 도구와 같은 방식). FCP · LCP가 사용자 체감에 가깝다. 대신 TBT가 기계 부하에 더 민감하다.
- `lighthouserc.json` 기본값은 **devtools**, `npm run lighthouse -- --method simulate`로 PSI 방식도 잰다.

## 8. TBT가 어디서 오나 — 남은 선택지 (사용자 결정 필요)

- 긴 작업은 ① react-dom 청크의 하이드레이션(작은 `/status/`도 4×에서 0.5~1.0초 한 덩어리) ② HTML 파싱 중 인라인 RSC 스크립트 · 첫 스타일 · 레이아웃(4×에서 0.3~1.2초 — 폴백 `@font-face` 14면 `local()` 조회 포함) ③ Next 라우터 초기화 · 프리페치 처리다. ①③은 Next 16 + React 19 App Router 런타임(초기 JS 138KB — D21)의 바닥이라 페이지 마크업으로 줄지 않는다.
- Lighthouse 4× CPU 모바일에서 TBT ≤ 200ms(성능 95 근처)는 이 구조(전체 트리 하이드레이션)로는 어렵다. 선택지:
  1. **(추천) NFR-01 판정을 지표 예산으로 바꾼다** — 'LCP ≤ 2.0s · CLS ≤ 0.05 · 초기 JS ≤ 160KB(이미 DR-11) + Lighthouse 성능 점수는 기록 · 회귀 감시(예: CI 러너 중앙값 ≥ 기준선 − 5)'. 사용자 체감 지표(LCP · CLS)는 지금도 예산 안이다. 비용 0.
  2. 점수 목표를 낮춘다(예: 모바일 ≥ 70 · 데스크톱 ≥ 95) — CI 러너 실측 뒤 숫자를 정한다(M5-08).
  3. 하이드레이션 줄이기(큰 작업, 위험 중~상): 숨은 라운드 · 접힌 일정 같은 정적 부분을 하이드레이션 밖 HTML로 렌더(`dangerouslySetInnerHTML` 정적 조각), 홈 위젯 두 벌 그리기(지면 · 마주 보는 면)를 한 벌 + CSS 배치로 — 화면은 같아도 구조 변경이라 별도 작업 · 시각 재검증 필요. 효과는 해 봐야 안다(하이드레이션 바닥 ①은 남는다).
  4. 라운드 창(FR-44 범위 — 2026-11-03 사용자가 이미 기각) · 클라이언트 렌더 전환 — 권하지 않는다.

## 9. M5-08(Lighthouse CI)에 넘길 것

- **명령**: `npm run build` → `npm run lighthouse -- --assert`(lhci collect + assert, 설정 `lighthouserc.json`). Playwright Chromium이 이미 설치된 잡에서 돈다(`npx playwright install --with-deps chromium`).
- **방식**: 기본 devtools. simulate는 우리 사이트에서 FCP · LCP를 폰트 때문에 2초 안팎 비관적으로 낸다(§2.1). PSI와 맞추려면 `--method simulate`를 따로 기록만.
- **대상 URL**: 스크립트 기본 10쪽(최신 날짜는 `data/news`에서 고름). CI 시간이 빠듯하면 홈 · 최신 날짜 · EPL · 바이에른 · `/tonight/` 5쪽 × 3회.
- **임계값**: 지금 `lighthouserc.json`의 assert는 NFR-01 그대로(성능 ≥ 0.95 · LCP ≤ 2000 · CLS ≤ 0.05, median-run) — **현재 모든 쪽이 성능에서 실패한다.** §8 결정 전까지는 성능을 `warn`(또는 기록만)으로, LCP · CLS만 `error`로 거는 것을 권한다. `/status/`는 `noindex`라 SEO 단언에서 뺀다.
- **변동 폭**: 이 기계(WSL · 부하 있음)에서 같은 쪽 TBT 774~7,743ms, 성능 48~81점, LCP ±0.4초. CI 러너는 더 조용하겠지만 3회 중앙값 + 성능 단언 여유(예: −5점)를 둔다. `benchmarkIndex`를 결과와 함께 남긴다.
